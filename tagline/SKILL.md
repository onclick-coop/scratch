---
name: tagline
description: A Claude Code PreToolUse hook on Bash that blocks any gh command writing an issue or pull request body, a comment, a review, or release notes that does not end with the project's attribution tagline. Use when wiring the attribution check into a project, when a gh command was blocked for a missing tagline, or when testing what the hook would decide for a command.
---

Rule: wire the tool into a project as a `PreToolUse` command hook with the matcher `Bash` in its `.claude/settings.json`, running `deno run --frozen --allow-read --allow-env=CLAUDE_PROJECT_DIR --config <path to scratch>/deno.json <path to scratch>/tagline/main.ts`
Reason: the hook blocks a gh call before it runs, both paths are absolute so the hook works from whatever directory the session is in, and without the env grant the tool blocks every gh body write

Rule: write the hook entry as `{ "hooks": { "PreToolUse": [{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "<the deno run line>", "timeout": 10 }] }] } }`
Reason: a matcher other than `Bash` never hands the tool a command, and the tool lets through any payload that is not a Bash call

Rule: pass the tool no arguments, and `--help` (`-h`) alone to print its usage
Reason: it reads the hook payload on stdin, and refuses any other option or argument

Rule: set the tagline in the `tools.config.json` at the project root under `tagline`, as `{ "tagline": { "text": "> _Generated with Claude_", "stale": ["_Generated by Claude_"] } }`
Reason: the tool reads the file from `CLAUDE_PROJECT_DIR`, which Claude Code sets to the root for every hook, and from the payload's `cwd` only when that variable is unset or empty

Rule: give `text` with no whitespace at either end, and list under `stale` the older spellings a writer should strip, or leave `stale` out
Reason: a blocked command's message lists the stale spellings, while the tool accepts only `text`

Rule: expect a key the section does not define, such as a misspelled `txt`, to be refused with the key named
Reason: the tool reads only `text` and `stale`, so a misspelling cannot pass as an absent setting

Rule: end every issue body, pull request body, comment, review, and set of release notes with the configured `text` as its last line, after a blank line
Reason: the tool passes a body only when its trimmed text ends with exactly that string on a line of its own with a blank line before it, unless the body is the tagline alone

Rule: pass a body as literal text or with `--body-file <path>` or `--notes-file <path>`, never through stdin
Reason: the tool reads the file at check time, while `--body-file -`, `-F -`, `body=@-`, and `--input -` cannot be seen and are blocked

Rule: write a body built at run time, such as one holding `$(...)` or a variable, to a file in an earlier step, such as the Write tool or a separate Bash call, and pass that file
Reason: the tool cannot know what the shell will put there, so it blocks the body with a message saying it is built at run time, and a file the same command fills that way is blocked too

Rule: pass a file path the shell does not have to expand, rather than one holding a variable such as `"$TMP/body.md"`
Reason: the tool blocks a path built at run time, since it cannot read a file it cannot name

Rule: expect a relative body file path to be read from the payload's `cwd`, moved by any literal `cd`, `pushd`, or `popd` earlier in the same command
Reason: that is where gh resolves the path, and a directory change whose target is built at run time, such as `cd "$DIR"` or a bare `cd`, blocks the relative path instead

Rule: write a body file the same command then posts with a quoted heredoc, or with `printf` or `echo` of literal text, through `>`, `>>`, `tee`, `cp`, or `mv`
Reason: the tool checks what those write instead of the file on disk, and blocks a file any other command writes first, or every file after a write whose target is built at run time

Rule: put the body among the fixed arguments when xargs runs gh, as `xargs -n 1 gh pr comment --body-file body.md`
Reason: the tool checks those arguments, and blocks a body-writing gh whose body or subcommand would come from xargs' input

Rule: post a comment, issue, or review through the REST commands, such as `gh issue comment` or `gh pr review` with `--body-file`, rather than a GraphQL mutation
Reason: the tool blocks every `gh api graphql` mutation that passes a `body`, since it cannot read that body reliably

Rule: read the block message on stderr to learn which subcommand, flag, and file failed
Reason: the message names each one, so the fix needs no further investigation

Rule: strip any stale spelling the message lists, append the tagline, and re-run the same command after a block
Reason: the hook keeps no state and re-checks the body on every call

Rule: expect exit 0 to allow the command and exit 2 to block it, with the stderr message handed back to the model
Reason: that is the Claude Code PreToolUse contract the hook targets

Rule: fix the setup the message names when a block reads "the tagline check cannot run" or "the tagline check failed", such as a missing or misspelled `tagline` section, then re-run the command
Reason: the tool blocks a body write it cannot check for any reason, while a command that writes no body passes without the config being read

Rule: check a command by hand with `deno task --config <path to scratch>/deno.json tagline < payload.json`, piping a PreToolUse payload that carries `tool_name`, `tool_input.command`, and `cwd`
Reason: the hook and a manual run take the same input, and a body write in a payload with no `cwd` is blocked since the tool cannot resolve its paths

Rule: unset `CLAUDE_PROJECT_DIR` for a manual run that should read the config in the payload's `cwd`
Reason: the variable wins over the payload, so one left set in the shell points the run at another directory's config

Rule: do not widen the hook's permissions beyond `--allow-read` and `--allow-env=CLAUDE_PROJECT_DIR`
Reason: the tool only reads stdin, that one variable, the config, and body files, and it runs on every Bash call

Rule: do not test the hook by invoking real `gh` against a live repository
Reason: a real invocation would create or edit actual issues, while a piped payload exercises the same decision
